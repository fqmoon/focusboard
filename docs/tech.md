# focusboard：技术

## 运行形态：为什么是浏览器

它必须能嵌进 agent 的工作流，而 agent 能用的输出通道只有三个：终端、聊天消息、文件。前两个显示不了图形，第三个要人主动去开。**浏览器是唯一同时满足「agent 能写、人已经在看、不用装东西」的显示面。**

- **不用桌面 GUI。** agent 跑在服务器上，窗口开不到人面前；跨平台、分发、更新全变成额外问题。
- **不用桌面产物。** 不做桌面 GUI、不打包成安装包；SDK 用 `tsc` 产出 ESM + 类型声明，源码和产物一一对应。
- **人不用切换场所。** 人本来就在浏览器里看文档、看网页、看 agent 的产出，板不应该要求再装一个东西。

SDK 只收一串元素，怎么送到页面由调用方决定：HTTP、SSE、文件、postMessage 都行。agent 不理解 UI 状态，只回答"现在这块板上有什么"。

这条决定了**全量重画**：渲染器不持有状态，每次按当前元素数组整张画出来，不会留下"改了一半"的中间态。

但全量重画说的是**渲染**，不是源码：元素数组是跨轮存活、持续维护的源码，agent 每次只改需要改的元素，不重写整块板。**重画 ≠ 重写。**

## SDK：core + 渲染器，单向依赖

这个项目是一个 SDK：一个 core，加上一个或多个渲染器。现在只有 `svg-render`。

```
  生成侧（模型 + skill）        —— 调用方，不在 SDK 里
       │  一串元素
       ▼
  core    规则库：元素模型、几何运算、查询、lint、档位、字格。纯计算，不碰 DOM。
       ▲
       │  单向依赖
  svg-render  渲染器：元素 + 档位 → SVG 字符串。不碰 DOM。
```

1. **core（规则库）** — 渲染无关。它定义这个项目的**规范**：什么算一块合法的板、什么算越界、一格多大、档位怎么选。能在 node 里跑。
2. **svg-render（渲染器之一）** — 把 core 的结果变成 SVG 字符串。现在只有它一个；以后要 canvas、终端或 PNG，是新增兄弟包，不是这个包里的分支。

**依赖是单向的：svg-render 依赖 core，core 的代码里不出现 svg-render 的任何概念** —— 不出现 SVG、DOM、px、字体、媒体查询。

反过来也有一条：**渲染器里不出现决策。** 它只做"把给定的矩形和线画出来"。一旦它开始判断"这里放不放得下""两个框要不要让开""这行要不要折"，解耦就漏了 —— 那些判断要么属于 core（可测），要么属于生成侧（讲法），不该有第三个落脚点。

拆分不是为了整洁，是为了两件事：

- **规则可以被测。** core 无副作用、无 DOM，测试就是在 node 里断言几何；不拆的话规则只活在像素里，没法断言。
- **规则可以换渲染器。** 终端 ASCII、PNG、甚至一个只打印坐标的调试渲染器，都是新增一个 `*-render` 包，core 一行不改。规则不跟渲染器一起死。

生成侧（模型 + skill）不在 SDK 里 —— 它是调用方，不是依赖。它决定画什么、放哪、讲多深。

**SDK 的边界是一块板。** 一个板实例就是一份元素数组 + 一个版面，它不知道也不关心别的板存在。多块板 = 多个独立实例：两个网页，或一个宿主页面嵌两块，怎么并置、切换、持久化全在 SDK 外面。所以契约里没有 `boardId`，也没有板列表和跨板引用。

**SDK 不存状态。** 跨轮维护的那份元素数组在调用方手里，每次调用全量传入；渲染器画完即忘。

**core 独占校验。** 板、元素、查询、lint 的 schema 只有一份，在 core 里；`lint()` 以它为准。工具 schema 不是第二份定义，只是对同一份 schema 的投影（`$ref`）；宿主可以换工具名和传输，但不能复制字段规则。接入方式（HTTP、SSE、MCP、文件）是外部的事。

校验分两级：**errors** 管形状和引用（类型、必填、枚举、整数、重复 id、悬空线），不成立就拒绝；**warnings** 管几何（越界、部分重叠、文字溢出、字格不整除），照画并报出来。两者都在 core，不允许宿主自己再写一套。

**几何是唯一真相，core 不持有意义，语义责任 100% 在生成侧。** 别人拿到这份几何能一模一样地重放，但不知道为什么。

## 实现栈

- TypeScript 5 + `tsc`，输出 ESM + `.d.ts`；不用 bundler。
- core 用 Ajv 8（draft 2020-12）校验唯一的 board schema；API 类型由 `json-schema-to-ts` 从同一份 schema 推导。
- 测试用 `node:test`，跑编译后的 JS。
- svg-render 只拼字符串，不碰 DOM。
- 示例宿主在 `examples/host`，只把 `board.json` 写成 SVG，不是运行时。

## 原语：只有两个

```
rect   矩形。边框和文本各自可选：无字的框、无框的文本、两者都有，都是同一个元素。
line  线。可带箭头（指定在哪端）。无向线不是省略了箭头，而是另一种语义。
```

框和线是程序开发图里的全部骨架。再加第三个原语（文字块、注释、图标、泳道），每一类都会带一整套属性、对齐规则和层级语义，成本指数上升。

**没有单独的文本元素：矩形框就是文本框。** 文本是 rect 的一个字段，没有独立坐标和身份；无边框、无填充的 rect 就是文本块。少一个原语，就少一整套"文本块怎么摆"的问题。

### 框是空间，不是节点

同一个矩形有几种用法，不需要区分：带文本 → 一个实体或一段说明；空的 → 占位或待定区域；包住别人 → 一块视觉上的区域；无边框 → 纯文本块。

但**元素始终是扁平的**：没有父子，也没有内外层。框与框之间是否构成包含，只是几何查询的一个结果，不是存下来的结构，也不改变数组的扁平性。

### 包含关系由生成侧维护

渲染器提供包含查询（`contains(a, b)`），只回答“A 的矩形是否严格包住 B”。

它不推断语义：视觉上压住不等于逻辑上属于。边界情况（压住一半、线穿框）会歧义，由生成方自己避免。

如果 agent 想把包含当成关系来用（“这几个属于同一个模块”），这层关系由 agent 维护：保证几何真的严格包含，并负责数组顺序 —— 想露出来的元素要写在覆盖它的框之后。**渲染器不替它记这层关系。**

lint 里也只做几何豁免：严格包含不报 `partial_overlap`，部分相交才报。这是为了不让包裹用的矩形天天报错，不代表渲染器承认了包含语义。

**有边框的矩形一律用低 alpha 填充。** `border:'none'` 不画边框也不填充；包裹用的矩形接近全透明，只留边框；普通矩形也用低透明度，不做不透明色块。这样即使数组顺序把外层矩形排在子元素之后，下面的内容也不会被遮死 —— agent 犯错时看到的是“层次不对”，而不是“内容没了”。这是 lint 不查顺序的缓冲，不是替代。

### 无向线是语义

- 有向：依赖、调用、数据流
- 无向：关联、并列、同属一组

少了无向线，并列关系只能靠位置暗示，位置一变语义就丢。

`a`、`b` 只是两端，顺序不带方向；方向只由 `arrow` 表达，值是 `'none'`、`'a'`、`'b'` 或 `'both'`，缺省 `'none'`。`'none'` 就是无向线，不是“忘了加箭头”。

线至少要用**实线 / 虚线**分两类，几乎零成本，能救掉一半读图时的混淆。

### 只有少量元素，让 agent 做选择题

模型画图失败不是因为不会画，是因为要做的决定太多。写 Mermaid 的 DSL 是填空题：节点要命名、边要选类型、缩进错一个字符就换一张图。

这里每一个决定都是选择题：

- **形状只有两个**：框、线。
- **尺寸只有几档**：占 4×2 格还是 6×3 格。
- **位置是整数格**：第 5 列第 2 行。
- **可选属性只有两个**：箭头在哪端、线是实线还是虚线。

答案空间小、可枚举，模型不容易答错；答错也可判 —— lint 一秒给结果。

位置是给的，不是算的。所以模型不需要具备布局能力，它只需要判断"这个该放哪"，而那是讲法，只有它能判断。

## 空间：固定页 + 格子

板是固定的一页，不是无限画布。这条同时定住两件事：

- **容量与渲染解耦。** 一份几何不依赖字体、像素密度和缩放：同一档下，手机和 4K 屏折同样的行、显示同样的字。
- **坐标可移植。** 同一档下的同一份几何在任何地方都是同一个东西，可回放、可比对、可 diff。

坐标用**格子**不用像素。格子解决三件事：容量可以数（还剩几格）；尺寸天然离散（模型从"算一个数"变成"选一个档"）；对齐自动成立。

它**不决定"该放哪"**。自动布局是"你给元素我算位置"，格子是"你给位置我只负责对齐"。

### 声明参数直白

生成方要说的东西只有这些，全是整数：

```
页：列数 × 行数（格子固定为正方形）
元素：x, y, w, h  ——  第几列、第几行、占几格
```

格子宽高比固定 1:1，所以页面是横是竖由列×行直接推出：18×27 竖、36×24 横、48×30 横。当前三组值先用，实测后再调。

没有容器元素、没有嵌套结构；也没有样式系统、主题和配置对象。`border` 只描述矩形画不画边、边是实线还是虚线，不描述它“是什么”。两个对象形状，几个字段，值全是整数。

画布宽高是推出来的结果，不是参数 —— 48 列 × 30 行、每格 100 单位 → 4800×3000，全是整数，没有魔法数。生成方永远不知道 4800 存在。

把参数压成离散的收益比看起来大：模型输出 `5`，不是输出 `483.7`。

### 档位：预设，浏览器测，生成前定

一页的列 × 行不是常量，是一个档位：

| 档 | 触发 | 列 × 行 |
|---|---|---|
| 小 | 窄视口 / 竖屏 | 18 × 27 |
| 中 | 默认 | 36 × 24 |
| 大 | 宽视口 / 投屏 | 48 × 30 |
| 绘图 | 调用方显式选（大屏） | 96 × 60 |

屏幕适配的三档跟视口走；绘图档不跟视口，由调用方在需要细节时显式选。它只是格子更密，没有新原语、没有新渲染路径，也不新增“跨格”能力。

小屏格子少，每格就大，字才读得清；把 96 列塞进手机，字会小到没法看。

**谁测：浏览器（屏幕三档）。** 只有它知道屏幕和容器多大。测的是**宿主容器**，不是 window —— 板可能嵌在侧栏、对话框、聊天窗口里，窗口宽不等于板宽。

```js
matchMedia('(max-width: 640px)').matches    // 小
matchMedia('(min-width: 1200px)').matches   // 大
new ResizeObserver(el => …)                 // 容器尺寸变了，重选
```

CSS 度量也可以用（容器查询 `@container`），但选档的结果最终要落成一个数字交给 JS —— 档位要参与几何，不能只活在样式里。

**交给生成侧。** 档位决定格线，几何要落在格线上，所以它必须在**动笔之前**确定，渲染层不能事后自己换。打开板时把档位报给 agent，agent 按这档的列 × 行生成。

**兜底。** 没测到（无 JS、首帧）用中档。

**可改。** 屏幕三档的断点、绘图档的列 × 行、内缩、圆角都在一个配置对象里，可覆盖：

```js
{ breakpoints: [640, 1200], tiers: [[18, 27], [36, 24], [48, 30]], drawingTier: [96, 60], inset: 2, radius: 3 }
```

**换档不做重排。** 板上已经有内容时改档，渲染器不会把现有几何重新排一遍 —— 没有这条代码路径，也不会有。重排要判断"哪个该放哪"，那是讲法，只有生成侧能判断。所以换档 = 让 agent 按新档重画一份。

于是耦合关系可以说准：**档位是页的参数，不是渲染的缩放。** 同一档下几何与设备无关；跨档是另一张图。

### 格子填充：几何贴边，边框内缩

元素占整格，几何边界和格线严格对齐 —— 位置、容量、lint 全都基于格线，一点也不含糊。

但**画出来的边框不贴格线**。渲染时边框在几何矩形内退让一个固定的小距离，并带一个小圆角：

```
几何    ┌──────┐     贴格线，整数格，可数可判
渲染     ╭────╮      内缩 2u + 圆角 0.18 格
```

这不是装饰。两个框放在相邻格（中间不留空）时，如果边框贴着格线画，两条边会重合，看起来像一条粗线，或者像连成了一个大框。内缩之后每个框都往里让一点，中间自然出现一道缝 —— **间距由渲染产生，不占格子**。

所以生成方不需要为了"别粘在一起"留空格子：那是浪费版面，而且会让"还剩几格"算错。放相邻格就行，视觉自己分开。

两条约束：

- **内缩必须小于半个格。** 否则相邻的框看起来不相邻，而几何上它们是挨着的，人会误判。
- **圆角按格给，线宽用物理像素。** 圆角 0.18 格、内缩 2u，两者都随页面缩放（4800u 的板缩到 1600px 时圆角约 6px）；线宽靠 SVG 的 `non-scaling-stroke` 固定为物理像素。不把圆角做成物理像素：纯字符串渲染器没有屏幕信息，缩到极小时圆角先消失反而比变粗更难看。

### 线：中心到中心，裁到边界

生成方只说 `a`、`b` 两个元素 id，不给坐标，也不给锚点。

渲染时的画法是固定的：

- 连线方向由**两个框的中心**决定；
- 线的两端**裁到各自的边框上**，箭头尖正落在框边，不进入框内；
- 裁剪要对**内缩后**的矩形做 —— 否则箭头会悬在那道缝里，看着没接上。

```
   ┌────┐              ┌────┐
   │ A  │─────────────▶│ B  │
   └────┘              └────┘
    中心 ──────────────── 中心   ← 只用来定方向和角度
    起点、终点裁在各自边框上
```

为什么是中心：

- **零参数。** 生成方只给 id，不用再算锚点 —— 连线因此保持为选择题（连哪两个），而不是填空题（从哪一点连到哪一点）。
- **永远接上。** 无论框多大、在哪，中心连线必然穿过两边框，不会出现悬空的线头。
- **可预测。** 同一对框、同样的相对位置，画出来永远一样，可以 diff。

已知代价：一个框的多条出边会在边框上同一处附近聚拢，看起来像从一点发散。这属于「锚点分散」要处理的事（见 roadmap）—— 不做自动路由，就不指望线自己避让。

三处分寸：

- **折行按累计列宽。** 一行放几个字由格子决定（一格两列）；不按像素折行，也不换字体换折法。
- **线宽和边框用物理像素。** 逻辑单位在缩放后才落到像素，4800 缩到 400 时一个逻辑单位不到 0.1 像素，细线会直接消失。
- **箭头按格子给，随板缩放。** 箭头长 0.55 格、半宽 0.22 格；短线上按 40% 收缩，免得两根相邻的框之间箭头吃满整条线。它和线宽不追求同一尺度：线要能看见，箭头要能看出来指向。

## 文字：列

文字不单独排版，直接铺在格子上，但**宽度的基本单位不是格，是列：一格两列**。

- **半角字占 1 列**（拉丁、数字、空格、窄标点）
- **全角字占 2 列**（CJK、全角标点、emoji）
- 一个 `w × h` 的框，可用宽度 = `2 × (w / s)` 列，行数 = `h / s`

用列而不是"半格"，是因为**所有数字都是整数**：容量 6 格写成 12 列，`abc` 是 3 列，`缓存层` 是 6 列。没有 0.5、没有四舍五入，写的人只需要数整数。

文字是 rect 的字段，不存在独立的文本元素；无边框的 rect 就是文本块。

元素可以带 `textScale`（整数，默认 1），字格就变成 `s × s` 个板格，列宽变成 `s/2` 个板格。它只改字的尺寸，不改元素几何；任何档位、任何框都能用，不是绘图档专属。要求 `w`、`h` 都能被 `s` 整除，除不尽由 lint 报"尺寸不是字格的整数倍"。

```
s=1，3×2 → 6 格 = 12 列：
┌───┬───┬───┐
│ 缓 │ 存 │ 层 │      缓=2列 存=2列 层=2列 → 6 列
├───┼───┼───┤
│ ab│cd │   │      abcd 各 1 列 → 4 列，剩 8 列
└───┴───┴───┘
```

- **折行按累计列宽。** `\n` 强制换行，否则累计到宽度上限（`2 × w / s` 列）就折。没有字宽表、行高、内边距这些参数。
- **只支持等宽排版。** 排版不依赖字形实际宽度：全角 2 列、半角 1 列，字形在自己的列区间里居中。字体族限定 monospace。
- **不补齐、不对齐整格。** 全角字接着前面的游标放，不为了"落进整格"腾出半格。所以英文串长度的奇偶会让后面的汉字**偏半格** —— 代价是同一缩进下的中文不一定上下对齐；换来的是没有空洞、没有四舍五入、数字全是整数。要汉字落在整格上，让它前面的半角字符（含空格）数是偶数就行。
- **字号比字格小一点，且两档不同。** 全角字 `0.72 × s × 格`，半角字 `0.78 × s × 格`。全角只占七成多，字才不撑满格子；半角要大一点，因为等宽字体的拉丁步进约 0.6 em，字号太小就重新散开。`textScale` 放大字格，不是画布缩放。
- **边框内缩不占列。** 边框画在内缩后的矩形上，字形在自己的列里再留一点物理像素的呼吸位，两者都不减容量。
- **溢出可判。** 累计列宽超过容量，lint 报"文字溢出"；`textScale` 不能整除尺寸也报；渲染裁切，不自动缩字号。

代价写在明处：半格是模型假设，不是字体承诺 —— 等宽字体的拉丁步进通常在 0.5–0.6 em 之间，未必正好一格的一半，所以极端字体下拉丁会略松或略紧。排版仍然不需要模拟字体度量：容量、折行、lint 全是数列。

> 历史：更早的模型是“一格一个字、拉丁占半格”，并按整格吸附对齐；`37eb1a1` 起改为列，不吸附、不补齐。旧讨论里的“半格对齐”“补齐整格”都作废。

## 契约：一串扁平元素

```js
{ id, type: 'rect',  x, y, w, h, text, textScale?, border?: 'solid' | 'dashed' | 'none' }
{ id, type: 'line', a, b, style?: 'solid' | 'dashed', arrow?: 'none' | 'a' | 'b' | 'both' }
```

- **没有父子关系，也没有内外层。** "谁在谁里面"是 `contains` 查询算出的几何结果，不是存下来的结构。
- **没有板间关系。** 连线只在同一块板的元素之间；跨板引用靠话说，不靠几何。
- **线不带文本。** 需要标签就在旁边放一个 `border: 'none'` 的 rect；线只连两端和箭头。
- **没有独立的 z 字段。** 数组顺序就是 z 序：读一条渲染一条，后写的压在前面的上面。渲染器不排序、不推断包含关系。
- **`border` 只描述矩形。** 缺省 `solid`；`dashed` 画虚线；`none` 不画边框和填充。三者几何、容量、lint 完全一致。它不表达“这是容器还是文本”，那是生成侧的语义。
- **没有布局算法。** 位置由生成方给，渲染器只负责画。

## 查询与 lint

```js
bounds(elements)      // 这批东西占了多大空间
overlaps(a, b)        // 会不会压到
contains(a, b)        // a 是否严格包住 b
hit(x, y)             // 这一点落在谁身上
free(region)          // 这块区域还剩几格
lint(board)           // 先验形状，再报几何；返回 { errors, warnings }
measure(board)        // 每个框的文字占了几列、几行、哪里偏半格
```

`measure()` 是纯函数，CLI 的 `check` 是它的外壳：每个框一行宽度、还余几列、有没有被自动折行、行数是否超过框高、哪些汉字偏了半格。**它只报告，不改盘，也不替生成方判断好不好看。**

同一个命令兼做点/区查询，一次调用可以问多处：`focusboard check board.json --free 17,10,15,9 --hit 24,12`。查询和提交一样吃整块板 —— 问的是生成方手里那一版，所以提交之前就能问；宿主持有“上一版”会引入版本歧义，也会让 SDK 变成有状态的东西。

命令行只有两个动词，区别是写不写盘：

| 命令 | 写盘 | 退出码 |
|---|---|---|
| `check` | 不写，只读 | 0 / 1（lint error）/ 2（用法错） |
| `submit` | 写 `board.svg`（`--page` 再加 `index.html`）；有 error 一个字节都不写 | 同上 |

两者默认输出 JSON，`--text` 换人读。板可以从文件或 stdin 读。

### lint 的输出

lint 分 errors 和 warnings。errors 是“这份输入不成立”，warnings 是“能画，但有问题”。

```json
{
  "errors": [
    { "code": "dangling_line", "ids": ["e1"], "message": "a 指向不存在的 r9" },
    { "code": "unknown_type", "ids": ["x1"], "message": "没有 circle 这种元素" }
  ],
  "warnings": [
    { "code": "text_overflow", "ids": ["r1"], "message": "文字溢出（8 行 > 6 行）" },
    { "code": "partial_overlap", "ids": ["r2", "r3"], "message": "部分重叠" }
  ]
}
```

**errors**：`missing_field`、`invalid_type`、`unknown_type`、`invalid_enum`、`not_integer`、`out_of_range`、`unknown_field`、`duplicate_id`、`dangling_line`。

**warnings**：`out_of_bounds`、`partial_overlap`、`text_overflow`、`text_scale_misaligned`。完全包含不算 overlap。

- errors 非空：输入不成立，调用方不应渲染。
- warnings：照画；越界裁到页边，溢出裁切，部分重叠按数组顺序遮挡，字格不整除按 floor 取整。
- `ids` 指到具体元素；`code` 是契约，`message` 只给人看。

lint 不判断样式和布局：对齐、留白、字号合不合适、两个框该不该挨着，都不报。这些用 `bounds` / `overlaps` / `contains` / `hit` / `free` 自己查，再由 agent 决定。

**还有一条边界要写死：线穿过 rect、线与线交叉，lint 也不报。** 线只连两个中心、两端裁到边框，中段对别的元素是透明的 —— 一条斜线从三个框中间穿过，几何上完全合法。这类问题只有看图才能发现，所以**"lint 0 warning"不等于"图看着对"**。要变成检查项，得先定"擦边算不算穿过"的口径（半格？内缩后的边框？），那是另一件事。

### 接口简单到不用训练

这些函数，名字就是语义。不需要文档、不需要 few-shot、不需要微调 —— 模型看名字就能用，而且可以在动笔之前先问 `free(region)` 还剩几格，这是普通函数调用。

对比一下要"学会"的接口：自动布局库要先建图、设节点、设边、跑布局、再取坐标，一次问答要组织五步调用；Mermaid 要先背对一门语法。这里的每一次调用就是一个问题。

「这张图讲清楚了吗」永远没有谓词。但「越界了吗」「压住了吗」「文字溢出了吗」「线悬空了吗」全是机械可判的。所以分层的真正用处在这里：**可验证的部分压到几何层，不可验证的部分（意图、取舍、讲法）浮给人。**

lint 是整个设计里唯一有 oracle 的地方，也是最容易被写坏的地方。

**能查的不要写成约定。** 约定会静默失效 —— 模型没读到、读了没照做，都不报错，只画出一张难看的图。所以越界、部分重叠、悬空线、文字溢出全部进 lint，并按 errors / warnings 分级；包含关系不是 lint 规则 —— 渲染器不判断谁该在谁里面。skill 只留真正查不了的。

## 交互机制

唯一的通道是说话：人不能操作板，只能聊天让 agent 改。三条推论：

1. **板是唯一的纠错通道。** 人唯一的反对方式还是说话，而说话要有东西可指，所以改动必须可见 —— 它不是便利，是唯一的兜底。
2. **每条都要能被自然语言指到。** 人失去了"指"的能力，只能说"那个跟缓存有关的"，所以每条要有能说出口的短标题，不能只有编号。
3. **改写必须显式。** 人说"这个不要"，agent 要落到具体哪一条，并表明自己理解成了哪条 —— 猜错时人能立刻发现。

第 2 条有代价：只能用文字重建指代。0.3.0 给的补丁是套索圈选 —— 人圈一块区域，拿到圈内元素的纯文本定位清单，贴回对话。**圈选是引用，不是编辑**，板仍然只有 agent 能改（见 roadmap）。

### 展开折叠是解释动作

人不要展开、不要折叠，**这是 agent 做的事**。所以折叠被翻译成对话：人说"这步不懂"，agent 展开这一支；人说"太细了"，agent 收拢。粒度由 agent 判断，人只表达困惑。

由此三条：

- **骨架必须稳定。** 元素顺序和相对位置不因展开深度变化而挪位，否则人每次都要重新找。
- **默认浅，深了才展开。** 深是成本，缺省不该付。展开要有理由：要么人问了，要么这里必卡。
- **收拢必须 agent 主动做。** 只展开不收，板会膨胀到一屏放不下，滚屏的问题全回来了。

**折叠要留痕迹。** 折起来不是丢内容，是让人以为没有内容 —— 所以折的地方必须有明确痕迹（数量、虚影、淡边）。这是折叠唯一的失败模式，也是最容易漏的地方。

### 板书是逐笔长的

它不是预先写好的文档，是当场生成、并且持续维护的同一块板。

- 观感上：一笔一笔出现，不是"唰"地换一版；
- 源码上：元素数组跨轮存活，agent 每次只改需要改的元素，不是每轮重写；
- 渲染上：无状态、全量重画——只要位置由格子保证不变，重画和逐笔在视觉上是一回事。

**重画 ≠ 重写。** 全量重画是渲染手段，不代表源码被丢弃。

### 一块板只讲一件事

板的价值是"讲到这里只用这张图"。一块板混两件事，就既讲不清也指不准。满了不是问题，混着讲才是。

## 非目标

不做自动布局，不做箭头交叉避让，不做语义校验，不存层级或包含关系，不做无限画布。

这些都能加，但加了 core 就膨胀到测不完 —— 而 core 能测完，是这里唯一值钱的东西。

# focusboard：产品

> **把话聊变成板书。**

一块给人和 agent 共用的板。讨论方案时，把消息流变成同一时刻摆在眼前的一张图。

## 使用场景

和 agent 讨论方案的整个期间，由 agent 维护一块或多块 board，板是双方共同的沟通面。

**每块板在形式上完全独立。** 一份元素数组、一个版面、一套几何；可以是一个网页，也可以是同一个宿主页面里嵌的两块。需要并置对照时（备选、现状、依赖），就再起一个实例，而不是把两件事挤进同一块板。

**本 SDK 只提供一块板的功能。** 开几块、怎么摆、怎么切换、人此刻看哪块，都是板外的事，由调用方决定 —— 可能是两个网页，也可能是一个页面嵌两块。这些不在本仓库范围内。

## 为什么做这个

我需要的不是"生成一张图的工具"，是"讨论时能一直看着的东西"。现成的三种都在解决别的问题：

- **Mermaid / PlantUML**：从文本源码生成一张成品图。适合写进文档，不适合当讨论现场 —— 它是编译，不是写字。
- **Excalidraw / 白板**：给人手画的。agent 画得慢，画得丑，而且控制不住位置。
- **聊天里贴图**：agent 每轮给一张新图，人无法确认改了哪 —— 因为没有"同一块板"这个概念，每张图都是从零开始的。

缺的是第四种：一个 agent 能持续往上面写、人只负责看和说的地方。这个仓库就是那个地方。

## 和 Mermaid、SVG 的区别

Mermaid 和 SVG 是最容易被拿来比较的两个对象，但问题正好相反：**Mermaid 把布局交给算法，SVG 把布局全推给生成方。**

| | Mermaid | SVG | focusboard |
|---|---|---|---|
| 输入 | 一门 DSL 源码 | 任意图形指令：坐标、路径、文本 | 一串坐标 + 两个形状 |
| 谁写 | 人维护，进版本库 | 人/生成器手写，或工具导出 | agent 持续维护同一份几何 |
| 布局 | 自动（dagre），你给关系它算位置 | 没有布局，自由度无边界，全靠生成方 | 你给位置，它只画；位置必须落格 |
| 同一份输入 | 换版本、换节点数，出图会变 | 渲染稳定，但语义相同的两次生成可以完全不同 | 几何是唯一真相，可 diff、可回放 |
| 能不能问 | 只给你一张 SVG | 不能，SVG 只是结果 | 能问还剩几格、谁压住谁 |
| 错了怎么知道 | 语法错静默成一张怪图 | 语法错会报，布局错不会 | lint 报越界、重叠、溢出 |
| 存在形式 | 一张要保存的图 | 一段要保存的标记 | 一块持续维护、每次全量重画的板 |

**Mermaid：布局由算法决定。** 同一个结构，自动布局出来的形状由算法决定，你说不出"这个放左下角，因为它是被否决的方案"。而在板书里，位置本身就是语义。

**SVG：自由度过高。** 它什么都能画，代价是每个决定都要生成方自己给：坐标、尺寸、字号、折行、层级、裁剪。自由度没有边界，也就没有可判定的错误 —— 画歪了、压住了、字溢出框，都仍然是合法的 SVG。模型不是画不出来，是要做的决定太多，每次都从零算一遍布局。

focusboard 把这份自由度收窄：两个原语、整数格、离散尺寸、字格容量、lint。**SVG 在这里是渲染目标，不是生成侧的输入。**

所以三者的目标不同：**Mermaid 产出一张图，SVG 画出一段图形，focusboard 承载一次讨论** —— 图是副产物，讨论才是主产品。

## 问题

和 agent 讨论方案，最后总会变成话聊。话聊不是不好，是它承载不了方案讨论：

- **只增不改。** 改一个结论只能再追加一段覆盖说明，越改越长。
- **位置不固定。** "上面那条"每次都指不同的东西，所有指代都得靠语言重建。
- **结论留不下来。** 聊完只剩记忆，没有东西可以指、可以改、可以复用。
- **看不见改了什么。** agent 说"我改了"，人无法确认它改成了什么。

四条合起来只有一个结果：讨论推进得越久，人越依赖自己的短期记忆，而短期记忆恰恰是最不可靠的地方。

## 为什么是板

人要理解一个方案，需要的不是更多文字，是同一时刻摆在眼前的一张图 —— 黑板上的板书。

板是**聚焦**用的：一块板跟一个正在讨论的主题，讨论到哪，板就停在哪。像几个人围着一张桌子，手边放几张纸，随手涂涂改改 —— 纸不是文件，是当前话题的工作面。

三件事因此成立：

1. **一块板一个主题。** 板上所有内容都为当前这个主题服务，不混着讲。
2. **涂改是常态。** 结论变了就改那一处，不是另起一张；源码跨轮维护，只有渲染是全量的。
3. **纸可以有好几张。** 焦点移到另一个主题、或者要并置对照，就再拿一张；焦点回来，还是原来那张。

**换板不是"写满了"，是"焦点变了"。** 名字取 focus，说的是这个：板跟着讨论的焦点走，人才不用在消息流里自己维持上下文。

## 档位与绘图模式

一页有边界，但手机和 4K 屏的"一页"不是一个量级。所以屏幕适配有三档：

| 档 | 屏幕 | 一页格子 |
|---|---|---|
| 小 | 手机 | 18 × 27 |
| 中 | 平板、笔记本 | 36 × 24 |
| 大 | 4K、投屏 | 48 × 30 |
| 绘图 | 大屏、桌面 | 96 × 60 |

前三档跟视口走；绘图档由调用方显式选，用于复杂示例图。

**绘图模式不是新东西**，就是格子更多的同一套模式：同样两个原语、同样的字格规则。格子多，同样的元素能摆得更细；字也更小，所以只在大屏上有意义。

框跨多格、用 `textScale` 放大字格，都是全局能力，不跟绘图档绑定。

框和文本跳多格是所有档位都有的能力，不是绘图档专属：3×2 的框在哪个档都装 6 个字，只是它在页面上占的比例不同。

档位只改一件事：一页能放多少格。小屏格子少，每格就大，字才读得清 —— 硬把 96 列塞进手机，字会小到没法看。

格子固定为正方形，所以档位同时决定了页面比例：18×27 竖版，36×24、48×30 和 96×60 横版。这些数是当前采用的起始值，实测后再调。

档位在**开始讨论之前**定下，一块板从头到尾是同一档。中途换档要按新档重画，不是放大缩小。

重排由 agent 重画一遍，板不做任何重排 —— 板不知道哪个该放哪，那是讲法。

同一档内，任何设备看到的都是同一张图（只是缩放不同）；跨档看到的是重排后的另一张。

## 人在这套东西里做什么

人不能直接改板，只能说话。所以人只做两件事：

- 说我不要哪个；
- 说我没看懂哪处。

其余全由 agent 维护：画什么、放哪、讲多深、什么时候擦、什么时候开新板、什么时候切回旧板。

这不是把人从判断里撤出来。AI 帮不上"选哪个"，但帮得上"每条路牺牲什么"。板的作用是**把人做判断的位置压缩到少数几个**。

（0.3.0 会给这条约束一个补丁：人可以圈选引用板上的东西，但不获得改的权力。见 roadmap。）

## 不做什么

- **不是画布。** 不无限延伸。一块板跟一个主题，焦点变了才开新板。
- **不是文档生成器。** 它不产出可交付的文档：板是讨论期间持续维护的同一张图，不是每轮重新生成的新图。
- **不是协作白板。** 没有多人、没有光标、没有评论。一个 agent、一块板；多块板就是多个独立实例，怎么组合不归 SDK 管。
- **不做自动布局。** 位置由画的人决定，板只负责对齐和画。
- **不替你判断讲清楚没有。** 那件事没有判据，只能由人当场说"不懂"。

## 什么样算成

- 讨论结束时，板上是一张能指着复述的图，而不是一段要靠回忆的对话。
- 需要并置对照时开了第二块，而不是把两件事挤进一块板。
- 换板跟着焦点走：不为省空间把两个主题挤在一块板，也不背着人另起一张重画。
- 人不需要记住任何东西，需要的时候看一眼就行。
- agent 改写之后，人一眼能看出改了哪一处。
